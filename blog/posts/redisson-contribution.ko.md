### Redisson 에 관한 짧은 소개와 Issue 해결 계기
 Redisson 은 Java 로 작성된 프로그램에서 Redis 를 활용할 수 있도록 다양한 API 를 제공하는 클라이언트 라이브러리이다. Lock TTL 을 자동으로 연장해주는 Watchdog 이라는 기능을 포함해, Lettuce 보다 조금 더 다양한 기능들을 제공한다.
그리고 Redis가 제공하는 다양한 자료구조들을 마치 Java 의 Collection 처럼 조작할 수 있도록 아주 Java 친화적으로 추상화한 API 를 제공하는데, 이 추상화 아이디어가 재밌어서 좋아하게 됐다.

내가 좋아하는 오픈 소스 라이브러리에 미약하게나마 도움이 되고 싶어 Issue 탭을 드나들기 시작했고, 눈에 잡히는 대로 사람들의 고민과 솔루션을 읽고 혼자 고민해보기도 했다. 해결하기 어려운 문제들이 대부분이었지만 아침에 신문에 실린 퍼즐을 푸는 것 같은 즐거움이었다. 

 그렇게 1년 가까이를 오가던 중, 나는 `bug`로 라벨링된 신기한 이슈 하나를 발견한다. 이 이슈의 다음과 같은 특징에 눈이 멈췄다.
> - Highly-concurrent 한 상황에서 간헐적으로 발생한다는 것.
> - 이미 4년 전에 동일한 문제가 Issue 로 제기되었고, 당시 Issue 제기자가 이미 해결책을 제안했다는 것
> - 그럼에도 아직 Fix 가 되지 않았다는 것.

 나는 금세 궁금한 것들이 몇 가지 떠올랐다. 이내 답을 하기 어려운 것들이었다.
> - 왜 가끔 발생할까?
> - 왜 동시 요청 부하가 큰 상황에서만 발생할까?
> - 해결책이 이미 제공되었음에도 왜 적용되지 않고 4년을 멈춰 있을까?
> - 결국 정확한 원인이 무엇일까?

대략 지난 1년 간, Redisson 라이브러리의 Issue 탭을 주기적으로 방문해 구경했다. Redisson 라이브러리를 처음 써보고 난 직후부터 그랬다.


 이 라이브러리가 좋았다. Redis 와 Client Program 이 소통하는 방식을 추상화한 방식이 유저 입장에서 아주 편리했기 때문이다. 그래서 레포 자체를 Clone 해서 코드를 살펴보기도 했다. 더 마음에 들었다. Spring Boot 를 활용한 WAS 개발을 하면서 마주치기 어려웠던 질문들을 할 수 있어 즐거웠기 때문이다. '왜 여기서 volatile 키워드를 사용했을까?'처럼 메인테이너 및 개발자의 생각을 나름대로 짐작해보기도 하고, '이 큰 라이브러리가 가장 처음 릴리즈되었을 땐 어떤 형태였을까?' 와 같이 사소한 것들도 궁금해해보기도 했다.


 그러다보니 이 Issue 탭 관찰하기는 나에게 꼭 신문의 십자말풀이 같은 것이 되었다. 버그로 보고된 이슈들의 원인이 무엇일지, 다른 사람들이 내놓은 풀이가 타당한지 혼자 풀어보는 게 재밌었다. 물론 대부분의 이슈에 대해선 조금의 실마리조차 찾지 못하는 것이 보통이었다. 하지만 못 풀어도 내 머리에 남는 것이 분명했기 때문에 아주 즐거운 시간들이었다.

사람들이 어떻게 버그를 찾았는지, 컨트리뷰터들이 원인을 어떤 방식으로 추적하고 어떻게 해결하는지 볼 수 있었고 그래서 혼자서라면 알기 어려웠을 것들을 배울 수 있었다.

예를 들어, 어떤 사람은 Redisson 을 활용하는 회사의 프로덕트 개발 작업을 하며 버그를 만나기도 하고, 어떤 버그는 간헐적으로 발생해 문제 재현 조차 어려운 것도 있었다.



기술적인 것 뿐만 아니라, 많은 사람들이 사용하는 프로그램을 모두가 달려들어 만들고 고치는 과정 자체를 따라가는 것에서도 , 메인테이너들이 이들과 어떻게 소통하고 작업하는지
